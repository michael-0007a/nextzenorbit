M1 · Domain split

How each host behaves

HostServesRedirects away (308, path and query kept)
nextzenorbit.com/, /privacy /terms /refund /compliance, static assetsLogin, register, dashboard and other client pages → app host. /admin* → admin host.
app.nextzenorbit.comAll (auth) and (dashboard) pages, client /api/*, PayU webhook, OAuth callback. / → dashboard, onboarding or login./admin* and /api/admin* → admin host.
admin.nextzenorbit.com/admin/*, /api/admin/*, the shared APIs the admin UI calls. Clean paths are rewritten internally: /users → /admin/users, /login → /admin/login. / → /admin.Client-only pages → app host.
nextzenorbit.vercel.app/api/* (webhooks, callback, and the extension during the transition)Pages → the matching new host.
localhost, preview URLsEverything, unchanged; treated as the app host plus admin pathsNone, so local development and previews keep working.

Session cookies

// src/lib/supabase/cookies.ts (new, tiny)
export function cookieOptionsFor(host: string) {
  const kind = hostKind(host);
  if (kind === "admin") return { name: "sb-orbit-admin" };              // host-only, separate session
  if (isProdDomain(host)) return { domain: ".nextzenorbit.com" };      // shared by apex + app
  return {};                                                            // localhost, previews: default
}

This is passed as cookieOptions to every Supabase SSR client: src/lib/supabase/middleware.ts, server.ts, client.ts (using location.host), and the inline client in src/middleware.ts. The admin host also receives the shared client cookie, but it only ever reads its own cookie name, so a client session never counts there.

The hostname is still not a security boundary. requireAdmin in src/lib/admin/guards.ts and the RLS policies stay unchanged.

M2 · Feature 2: client ↔ team messaging

One thread per client. The client writes from the app host; any admin assigned to that client (through client_admin_assignments) replies from the admin host.

  • Migration 044_client_messages.sql: client_messages(id, client_id, sender_id, sender_role, body text ≤ 4000, created_at, read_at). RLS: a client can select and insert only where client_id = auth.uid() and sender_id = auth.uid(). Admin access goes through API routes that check the assignment. Index on (client_id, created_at). ME
  • Client API GET/POST /api/messages, with rateLimit() from src/lib/rate-limit.ts. Admin API GET/POST /api/admin/users/[id]/messages guarded by requireAdmin plus the assignment check in src/lib/admin/assignments.ts. Super admins can see every thread. ME
  • When a message is sent, insert a row into the existing notifications table for the other side, so it shows up in the current notification UI. ME
  • Client UI: a "Messages" page in the dashboard nav with an unread badge. Admin UI: a "Messages" tab on the client detail page, plus an "unread threads" list on the admin home page. ME
  • Live updates: poll every 10 seconds while the thread is open (shortcut: comment noting it). Upgrade to Supabase Realtime if message volume grows. ME
  • Tests: a client can't read another client's thread; an unassigned admin is refused; an assigned admin can reply; body length is capped. Use the RLS test against a Supabase branch or PGlite. ME

M3 · Feature 3: LinkedIn profile optimizer

  • POST /api/linkedin/optimize takes { resumeId, targetRole }, loads the resume (owner check), and calls the AI writer model (built on Amazon Bedrock, Kimi K2.5; this plan originally said Groq). The zod output schema: headline (≤ 220 characters), about (≤ 2,600), top skills (≤ 15), and 2–3 rewritten bullets per experience entry. Logs to ai_usage, is rate-limited, and (since migration 046) counts against the daily light AI allowance. ME
  • Prompt file in src/lib/ai/prompts/, using the same JSON-output pattern as the resume prompts. ME
  • Page /linkedin: pick a resume and a target role, generate, then sections with copy buttons and character counters, plus a regenerate button for each section. Nothing is saved in v1. ME
  • Test: the parser rejects output that's too long or malformed. ME

M3 · Feature 4: CTC to in-hand and offer comparison

Runs entirely in the browser, with no AI cost and no new tables. Offers are saved in localStorage in v1.

  • src/lib/salary/ctc.ts, pure functions that work out: basic (as a % of CTC), HRA, employer and employee PF (12%, with an optional ₹15,000 wage cap), gratuity (4.81% of basic), professional tax (state picker, default ₹2,400 a year), variable pay, and new and old regime tax with 4% cess, the 87A rebate and surcharge. The output is monthly in-hand pay and a yearly breakdown. ME
  • Tax slabs live in one constant table labelled with the financial year. Check the current year's slabs and rebate limit against the Income Tax Department site before launch. ME to draft, YOU or a CA to sign off
  • Page /offers: 1–3 offer cards (CTC, basic %, variable, joining bonus, notice buyout, regime) side by side, with "best in-hand", "best first-year" and differences highlighted. ME
  • Tests: assert-based cases for known salaries (zero tax under the rebate limit, a high earner with surcharge, the PF cap on and off). ME

M4 · Feature 5: AI mock interviews (basic)

Text only. A session is 5 questions: up to 3 from the existing interview_questions bank for the user's career, and the rest generated from a pasted job description or a tracked application.

  • Migration 045_mock_interviews.sql: as built: mock_interviews(id, user_id, role, job_description, questions jsonb, answers jsonb, overall int, created_at, completed_at), server-only (RLS on, no policies). ME
  • POST /api/mock-interviews creates a session and its questions. POST /api/mock-interviews/[id]/answer scores one answer (zod: score 1–5, strengths, gaps, improved answer). As built, there is no separate /complete call: the last answer writes the overall score and completed_at. Uses the Bedrock writer model and is rate-limited. ME
  • Page /interviews/mock: setup, one question at a time with an optional timer, feedback after each answer, a final scorecard, and a list of past sessions. ME
  • Tests: owner-only access, and the scoring parser rejects bad output. ME
  • Later, not in this plan: voice answers and adaptive follow-up questions. ME
