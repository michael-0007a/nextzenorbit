How this works read once

  • One Vercel project, one deployment, many domains. You do not need three deployments. All domains point at the same app, and the code looks at which domain a visitor used to decide what to show: the homepage, the client app or the admin console.
  • Production vs preview. Vercel builds production only from main. Every other branch, like beta, gets its own separate preview build at its own address. Pushing to beta can never change the live site.
  • Safety switch. The domain split is off unless all three of NEXT_PUBLIC_SITE_URL, NEXT_PUBLIC_APP_URL and NEXT_PUBLIC_ADMIN_URL are set. Without them, the app works exactly as it does today, plus the new features. A test covers this.
  • Same database. Beta uses your real Supabase database. That's fine because the new migrations only add tables, but it means everything you do on beta is real: use test accounts, never message real clients, and don't test payments on beta.
  • Beta domains mirror production exactly, so testing beta tests the real setup:
    PartBetaProduction (later)
    Homepagebeta.nextzenorbit.comnextzenorbit.com
    Client appapp.beta.nextzenorbit.comapp.nextzenorbit.com
    Adminadmin.beta.nextzenorbit.comadmin.nextzenorbit.com
    The app domain must sit under the homepage domain (app.X under X) for the homepage and app to share one login. That's why it's app.beta… and not beta-app….

8 · If something breaks after going live: rollback

  • Supabase: set the Site URL back to https://nextzenorbit.vercel.app.
  • Nothing in the database needs undoing; the new tables can stay.
