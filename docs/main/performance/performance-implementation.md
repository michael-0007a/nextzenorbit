## Measurements and limits

Public live baseline: `performance-baseline-2026-10-05.json`, five anonymous requests per route, measured before deployment. Homepage p50/p95 first byte: **302 / 2,688 ms**, with cache misses and `bom1::iad1` placement. Terms: **98 / 844 ms**; admin login: **66 / 306 ms**. Five samples are a small baseline; the first request includes connection setup and is not proof of a Vercel cold start.

Local production smoke baseline: `performance-local-2026-10-05.json`. Homepage p50/p95 first byte: **9 / 63 ms**. This is a different environment and is **not** a production speedup claim. Public pages rendered without browser console errors; a signed-out dashboard visit redirected to login. Mobile homepage DOM showed no horizontal overflow.

Resume layout benchmark: 60 iterations per synthetic fixture, same local Node runtime and unchanged layout/export semantics. These measure the layout calculation, not browser paint or AI generation.

1. Review the changes and apply **040_performance_read_models.sql**, then **041_document_jobs.sql**, using the normal Supabase migration workflow. Both are transactional and additive. Do not edit migrations 001–039 or replay historical migrations blindly. Verify migration order against the actual migration ledger before running a general `db push`.
2. Keep the existing Supabase and AI environment values (now Bedrock: `AWS_BEARER_TOKEN_BEDROCK`, `AWS_REGION`). The free-tier setup does not schedule a Vercel cron and does not require a new `CRON_SECRET`.
3. Deploy this checkout to Vercel. `regions: ["bom1"]` applies to new function deployments. Inspect function placement separately from middleware/CDN placement. See [Vercel regions](https://vercel.com/docs/functions/configuring-functions/region).
4. New jobs run immediately through Next's request-managed `after()`; active owner polling recovers ready/expired leases. If the browser closes and a worker is interrupted, the job remains persisted and recovery resumes when its owner reopens progress. There is no unattended scheduled recovery in this configuration. The protected `/api/internal/jobs` endpoint remains an optional manual maintenance hook: only if explicitly used, configure `CRON_SECRET` and send its matching Bearer header. It recovers up to two jobs and removes terminal jobs older than seven days per invocation; cleanup is not automatic without a caller. See [Next `after`](https://nextjs.org/docs/app/api-reference/functions/after).

## Rolling compatibility and rollback

Before migration 040 is installed, only a missing-function error enables legacy read fallbacks; unrelated database/authorization failures are not silently bypassed. Legacy fallbacks retain their previous large-list limits, so database pagination/aggregation improvements require the migration. Before migration 041, workspace generation falls back to the synchronous path. Install migrations before expecting the full performance behavior.

If the deployment regresses a business flow, restore the previous Vercel deployment and investigate with stage timings. Leave the additive read-model functions, indexes, and job table in place during a code rollback; deleting them or changing RLS during an incident is unnecessary. The signed access envelope is internal, expires after 30 seconds, and is never a permission cookie or a public response header. Private authorization is never globally cached.
