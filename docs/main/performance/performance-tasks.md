## First batch: quickest improvements

- [ ] **P01 — Record a small production baseline.** Measure dashboard, admin users, client detail, apply queue, career detail, and resume generation. Use the same accounts and dataset for before/after comparisons; separate cold and warm requests. Record first byte, useful-content time, API durations, request count, and response bytes. Add stage timing for auth, database, model, and export without logging personal content. Done when the slowest stages are identifiable and results are saved.
- [ ] **P02 — Align Vercel functions with the Mumbai database.** Confirm Supabase region and current Vercel function regions. Configure applicable functions for `bom1`, redeploy, and verify runtime placement. September 29 homepage headers showed `bom1::iad1`. Routing middleware has separate placement behavior, so measure it independently. Done when relevant functions run near the database and equivalent requests have been compared. [Vercel region configuration](https://vercel.com/docs/functions/configuring-functions/region)
- [x] **P03 — Remove the initial 300 ms delay on Admin Users.** Fetch immediately on first load, debounce subsequent search typing only, and cancel obsolete searches. Target: `src/app/(admin)/admin/users/client.tsx`. Done when first load has no timer delay and a slower old search cannot replace a newer result.
- [x] **P04 — Fetch independent data concurrently.** Start with admin client details, applications, and the two resume lists; follow with career projects and roadmap work. Preserve authorization before releasing private data and retain section-level error behavior. Done when independent requests overlap in traces and existing results remain correct.
- [x] **P05 — Reuse authentication and role reads within server rendering.** Use the existing cached user helper consistently and memoize the admin guard per render request. Target shared Supabase helpers, admin guards, layouts, and pages. Done when layout/page calls no longer repeat equivalent reads within one render. Verify role changes, suspension, and signed-out behavior. React memoization does not span middleware and route rendering automatically.
- [x] **P06 — Add immediate navigation feedback.** Add dashboard/admin loading boundaries and section-level Suspense where useful; check production prefetch behavior. Keep layouts from waiting for optional data. Done when navigation shows feedback promptly and slower optional panels do not hold back ready content. This improves perceived speed separately from backend latency. [Next.js navigation guidance](https://nextjs.org/docs/app/getting-started/linking-and-navigating)

P03–P20 implementation is present. P01, P02, P13, P16, P18 and P21 retain production measurement/activation requirements; no live deployment has been made.

## Second batch: reduce work on every visit

- [x] **P07 — Consolidate approval/payment checks.** Build one authoritative account-access lookup with explicit role, suspension, approval, block, and subscription semantics. Remove redundant database work across middleware, layouts, and APIs through a deliberate access-layer design. Keep checks at protected data/mutation boundaries and retain RLS. Do not trust user-supplied access headers or globally cache permissions. Done when the query count falls and pending, blocked, unpaid, expired, suspended, regular, and privileged accounts retain correct access.
- [x] **P08 — Remove per-admin query loops from analytics.** Replace six initial queries plus three queries per admin with a fixed number of grouped database queries/functions. Target `src/app/api/admin/stats/route.ts`. Done when adding admins does not add three requests per admin and totals match the old implementation on fixtures.
- [x] **P09 — Paginate and filter in the database.** Cover apply queue, admin users, client job history, applications, and analytics history. Apply assignment/status filters before pagination, fetch job details on expansion, and return aggregate counts separately. Done when payloads stay bounded as data grows and permissions, ordering, counts, and page boundaries remain correct.
- [x] **P10 — Reduce response payloads.** Remove full resume content from client-list/detail responses that only display metadata; avoid duplicating the base resume payload. Replace unnecessary `select('*')` calls with required columns. Done when list endpoints contain no unused document bodies and editing/export still fetch their required content.
- [x] **P11 — Supply initial admin data on the server.** Prioritize Users, Team, Analytics, and User Details. Seed interactive client components with initial results; keep filtering and refresh interactive. Done when initial content does not require a browser effect followed by another API/auth round trip.
- [x] **P12 — Share subscription and client query state.** Seed a shared subscription provider from server data and refresh after payment/subscription changes. Reuse list results when navigating back where appropriate; invalidate after writes and clear on sign-out/account change. Done when sidebar/page consumers avoid duplicate subscription fetches and stale privileges are never used for server authorization.
- [ ] **P13 — Tune measured slow queries and RLS.** Inspect live indexes, query statistics, and execution plans. Evaluate indexes matching `claimed_by/status` and `user_id/created_at` access patterns, and per-statement evaluation of row-independent entitlement functions. Use new migrations rather than editing applied migrations. Done when plans demonstrate the improvement and allow/deny tests pass. Service-role requests and RLS-scoped requests need separate analysis.

## Third batch: public pages, caching, and browser performance

- [x] **P14 — Make public marketing content statically deliverable.** Separate public content from cookie/auth-dependent rendering while preserving login errors and signed-in navigation. Done when repeat public requests benefit from static delivery without exposing personalized responses.
- [x] **P15 — Cache shared reference data with explicit invalidation.** Prioritize careers, roadmaps, interview resources, and shared catalog data. Separate authorization from cacheable content; exclude personal notes/projects and privileged responses from public caching. Done when repeated authorized reads avoid equivalent database work and edits invalidate affected entries.
- [ ] **P16 — Optimize images and route JavaScript from browser measurements.** Measure actual optimized hero-image bytes, add accurate responsive sizes, re-encode/resize the source if worthwhile, and identify which modules reach each initial route bundle. Lazy-load optional editors/dialogs where this improves initial loading. Done when transferred bytes and main-thread work fall without layout/image regressions.
- [x] **P17 — Keep long-resume editing responsive.** Profile whole-form serialization and preview pagination; defer/debounce preview updates and isolate rerenders. Use a Web Worker only if profiling justifies it. Profile large blur/animation effects on modest phones too. Done when typing and scrolling remain responsive with realistic long documents and exported layout remains correct.

## Resume generation and exports: measure separately

- [ ] **P18 — Reduce AI time while preserving output quality.** Measure initial generation and optional page-fit revision separately. Evaluate prompt size, task-appropriate output budgets, and any model change against factuality, completeness, and layout fixtures. Keep bounded retries and explicit timeouts. Done when representative generation is faster without increased truncation, invented facts, or broken JSON. A lower maximum token setting alone does not guarantee faster output.
- [x] **P19 — Optimize upload/parsing and repeat exports.** Reuse direct signed-upload patterns where suitable, avoid unnecessary sequential storage/local-file work, and measure extraction separately from AI parsing. Cache private exports by document content, template, format, and renderer version; load only the selected export library where beneficial. Done when repeat exports reuse valid artifacts and changed documents never receive stale files.
- [x] **P20 — Add durable jobs only where long requests warrant them.** For parsing, generation, or batch export, choose a compatible managed job runner/queue within the existing stack constraints. Persist job state, use idempotency, bounded retries, and progress updates. Do not use an unawaited in-process promise as a queue. Done when jobs survive request interruption, users can resume progress, and retries do not duplicate charges/documents. Progress improves waiting experience; it does not itself shorten model computation.

## Completion checks

- [ ] **P21 — Verify and publish measured results after each batch.** Run the production build, relevant auth/payment/assignment and resume regression checks, then compare the same representative requests and devices. Record p50/p95, errors, request counts, payload sizes, and AI duration separately. Deploy in small batches with rollback available; investigate regressions before proceeding.

Suggested initial goals, not current results or promises: navigation feedback near 100 ms, useful warm dashboard content near one second on a good connection, and common warm read APIs below 500 ms at p95 where practical. Refine budgets after P01. Set AI targets only after measuring real document lengths and quality requirements.

Increase Vercel or Supabase compute only if CPU, memory, connection, or concurrency measurements show saturation. Infrastructure upgrades are a conditional follow-up, not a substitute for completing the high-priority tasks.
